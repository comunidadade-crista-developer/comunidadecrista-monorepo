# ADR-015 — Admin: criação, promoção e sessão

**Data**: 2026-11-17
**Estado**: Aceite
**Código**: `services/admin-roles.ts` · `scripts/admin-promote.ts` · `scripts/admin-demote.ts` · `services/admin.ts` · `routes/admin.ts` · `auth/middleware.ts` (`requireAdmin`) · migrações `0005` e `0006`
**Complementa**: [ADR-010](ADR-010.md) (admin na mesma app, role `admin`)

## Contexto

O sistema precisa de moderadores. A tabela `users` já tem `role: 'user' | 'admin'`, o `requireAdmin` revalida o role na base de dados em cada pedido e o `moderation_log` já está modelado. Falta decidir:

1. Como existe o **primeiro** admin?
2. Como se promove e despromove depois?
3. Como se autentica o admin (mesmo login? rota separada? segundo factor?)

## Decisão — o primeiro admin e as promoções

**Só por linha de comandos, executada por quem tem acesso ao servidor.** Não há endpoint HTTP, nem seed automático, nem variável de ambiente.

```
pnpm --filter @comunidade/api admin:promote <username>
pnpm --filter @comunidade/api admin:demote  <username>
```

Princípio: **acções que aumentam privilégio não passam por HTTP.** Se o painel admin for comprometido, não consegue criar mais admins; só quem tem shell no servidor.

### `admin:promote`

1. O utilizador tem de existir e **não** estar apagado nem em apagamento pendente.
2. Já é admin → avisa e termina com sucesso (idempotente).
3. Passa a `role = 'admin'`.
4. **Revoga todos os refresh tokens** do utilizador (as sessões antigas deixam de renovar; o novo login traz o role certo).
5. Regista `admin.promoted` em `moderation_log` (`moderator_id` nulo = acção do sistema; `target_user_id` = o promovido).
6. Os passos 3 a 5 são **uma só transacção**.

### `admin:demote`

1. Mesmas validações de existência; se não for admin, avisa e termina com sucesso.
2. **Recusa despromover o último admin** (conta só admins activos: não apagados e sem apagamento pendente). A verificação e a escrita ficam sob um bloqueio da base de dados (advisory lock transaccional, partilhado com o pedido de apagamento de conta), para dois `demote` ou um `demote` e um apagamento em simultâneo não deixarem zero admins.
3. Passa a `role = 'user'`, revoga os refresh tokens e regista `admin.demoted`.

Códigos de saída: `0` sucesso (incluindo «nada a fazer»), `1` erro de uso ou de ambiente, `2` utilizador inexistente ou inactivo, `3` recusado (último admin).

A lógica vive em `services/admin-roles.ts` (testável); os scripts só lêem argumentos, ligam à base de dados e traduzem o resultado em saída e código.

### Alternativas rejeitadas

- **Variável `ADMIN_USERNAME` que promove no arranque**: se o username for registado por um atacante antes do deploy, este fica admin; não escala para vários admins; não deixa registo explícito.
- **O primeiro utilizador registado é admin**: qualquer pessoa que descobrisse a app antes do operador ficaria admin; em produção o registo é público.
- **`POST /admin/promote`**: contraria o princípio acima.

## Decisão — autenticação

**Mesmo login e mesma sessão; sem rota nem fluxo separados no MVP.** Uma segunda superfície de autenticação seria uma segunda superfície de ataque, sem a robustez já feita no login normal (limites, argon2id, protecção de tempo).

Mitigações:

- O `requireAdmin` **revalida na base de dados em cada pedido** (role actual, conta não apagada e sem apagamento pendente): um token roubado de alguém despromovido falha no pedido seguinte.
- Access token de 15 minutos; refresh rotativo com detecção de reutilização.
- As rotas `/admin/*` têm limites próprios por administrador (leitura e escrita).
- Segundo factor (TOTP) fica para depois do MVP; não bloqueia.

## Decisão — API do painel

Backend sob `/admin/*`, com `requireAuth` + `requireAdmin`, ambos em `preValidation` (o 401/403 precede o 400 de validação).

| Método | Rota                       | Função                                                                    |
| ------ | -------------------------- | ------------------------------------------------------------------------- |
| GET    | `/admin/posts`             | Fila de revisão (`status`, por omissão `pending_review`, do mais antigo). |
| GET    | `/admin/posts/:id`         | Detalhe, denúncias e decisões anteriores.                                 |
| POST   | `/admin/posts/:id/approve` | Publica. Só a partir de `pending_review`.                                 |
| POST   | `/admin/posts/:id/reject`  | Rejeita com motivo (10–500 caracteres). Só a partir de `pending_review`.  |
| GET    | `/admin/reports`           | Denúncias por estado (por omissão `open`).                                |
| GET    | `/admin/moderation-log`    | Auditoria (filtros `action` e `postId`).                                  |

Regras:

- **Só se decide sobre `pending_review`.** Um post `hidden` (suspenso por apagamento de conta, ADR-012) não é «aprovável»: ressuscitá-lo contornaria a suspensão. Outro estado dá `409 invalid_state`.
- Decidir um post é **uma transacção**: bloqueio da linha (`FOR UPDATE`), mudança de estado, resolução das denúncias abertas (`resolved_kept` ao aprovar, `resolved_removed` ao rejeitar), entrada no registo de auditoria e evento no outbox (`post.approved` / `post.rejected`). Depois do commit invalida-se a cache do feed.
- Dois admins a decidir o mesmo post em simultâneo: o segundo vê o estado já mudado e recebe `409`.
- As listagens usam **cursores compostos opacos**, um tipo por lista (`admin_posts`, `admin_reports`, `admin_log`); um cursor inválido ou de outra lista é `400`.
- Autores, denunciantes e moderadores saem pelo `username` (`null` = removido), nunca por identificador.
- O registo de auditoria guarda-se sem prazo: não contém IPs, só quem, o quê e quando. As chaves estrangeiras são `ON DELETE SET NULL`, por isso a purga de contas ou de posts não apaga o registo.
- O motivo da rejeição **não** é mostrado ao autor nesta fase (será exposto nas rotas `/users/me/posts`).

## Consequências

- Um operador sem acesso ao servidor não consegue ficar admin; recuperar o acesso admin perdido exige shell.
- Não há interface para gerir admins: é intencional.
- O painel (`apps/web`) fica para uma fase própria; este ADR fixa só o contrato do backend.
